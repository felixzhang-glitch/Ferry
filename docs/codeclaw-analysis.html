1. 项目定位

codeClaw 是一个刻意做薄的桥接层：把飞书/微信上的聊天消息转发给本机 CLI 编码 agent（默认 pi），再把 agent 的回答按渠道语义（Markdown 卡片 / 分段 / 图片）返回给用户。它不是智能体框架，不实现 prompt 工程、RAG、workflow——这些能力由后端 CLI 原生承载。

设计哲学（一次说透）：
  • 不造智能：会话记忆、上下文压缩、工具调用全部由 CLI agent 原生负责，桥接层零重复实现。
  • 只做编排：消息收发、渠道适配（格式化/分段/长连接/图片上传/文件归档）、后端路由切换、轻量命令系统。
  • 可切换性：运行时在 pi / opencode / codex / claude / qodercli 五个后端之间切换，持久化到磁盘，重启保留。

职责边界

做（harness 职责）
  • 飞书 WebSocket 长连接 + 微信长轮询接入
  • 消息去重、命令分发、会话级串行队列
  • Markdown 卡片渲染 / 超长文本分段 / 图片上传
  • 文件消息自动归档（飞书直接下载、微信 AES 解密）
  • 定时提醒与每日简报
  • 多后端路由、进程生命周期管理（启动/超时/取消/熔断）
  • 时间感知注入、规则/技能/长期记忆注入
不做（agent 职责）
  • 不做 prompt 工程（原文透传给后端）
  • 不做 RAG / 知识库
  • 不做多租户 / 权限系统（个人项目单实例）
  • 不做 agent 编排 / workflow 引擎
  • 不为后端原生能力写自己的实现

关键设计特征

  • 统一 Protocol 抽象（core/agent/types.py）：后端客户端与 AgentRouter 全部实现 BackendClient 鸭子类型，handler 只依赖协议不依赖具体类，新增后端不改路由器。
  • 进程即会话边界：CLI 每轮一个新进程，长时任务靠 trace_id 追踪，可通过 /stop 杀进程组。
  • 结构化日志：全链路 JSON 日志，统一携带 trace_id / duration_ms / event / status_code，事件名形如 pi.stream / feishu.reply / queue.job_error。
  • Fail-open 原则：记忆渲染、时间注入、规则加载等辅助能力出错只记 warning，绝不打断对话。

记忆注入（app/memory.py 的细节）

  • 「写入协议」必须每轮在场——因为 opencode 的 preamble 只发首轮，所以协议走常驻通道而非首轮注入。pi 后端用 --append-system-prompt，opencode 用 instructions，claude 家族用 load_system_rules() 合并。
  • 记忆内容受 MEMORY_MAX_INJECT_CHARS 预算约束（按类别边界截断），协议本体始终完整注入——“被截半的规则比没有规则更危险”。
  • 快照仓 git dir 放在 runtime/memory-git，迁移逻辑处理了历史遗留的嵌入 memory/.git；无 remote 因而物理上不可推送。
  • 快照时机：每轮渲染前 auto_commit() 捕获上一轮写入（滞后一轮，作为防误写兜底）+ shutdown 再快照一次。

飞书回复降级链（handler.py 的健壮性）

  1. 回复优先 reply_markdown（卡片）→ 失败降级 reply_text → 再失败走 send_markdown 按 chat 分发 → 最终按文本分段逐条发送。
  2. 图片回复：reply_image 失败自动 fallback 到 send_image。
  3. 收到消息立即发 Typing reaction 作为快速 ack（Quick Ack）。

生成图片自动推送（handler.py 的特色功能）

消息文本命中「画/图/image/draw」等关键词时，启动一个 watcher 协程：每 1s 扫描 ~/.codex/generated_images 时间窗内的新图，发现即推送；随后可自动 cancel 仍在跑的 agent（auto_complete_on_image），实现"图生成完即送达"。

微信（channel/wechat/handler.py）

  • webhook 校验 Authorization: Bearer <WECHAT_WEBHOOK_TOKEN>。
  • 与飞书共享命令系统，但明确不支持 /remind（返回提示改用飞书）。
  • webhook 请求 挂起直到任务完成 再返回 replies 数组，sidecar 收到后逐条回发——回复与消息强制一一对应。
  • 并发控制更紧（队列 max_pending=3），且不支持 /skills 之外的图片链路。

pi 后端的三个"已实测"陷阱（代码注释与文档双重强调）

  1. 退出码恒为 0：认证失败也 exit 0。成功与否只能看事件流里最后一条 assistant message_end.stopReason（error/aborted 即失败），即使已流出部分文本。
  2. message_end 对 user 轮也会触发：必须判 role == "assistant"，否则会把用户提问当回复回显。
  3. thinking/toolcall delta 一律丢弃：只有 type == "text_delta" 进入回复。

另外 pi 支持进程内 auto-retry：中间失败后重试成功不算失败（last-wins 判定），错误事件本身不能直接抛异常。

通用基础设施（每个客户端内置）

  • 熔断器：连续失败 ≥ 阈值（默认 5）打开，冷却期内直接拒请求。
  • 重试：指数退避；认证类错误（unauthorized/auth/circuit breaker）不重试。
  • 进程管控：start_new_session=True + 进程组 SIGKILL，/stop 经 trace_id 杀进程；stdin=DEVNULL（防 supervisor stdin 管道阻塞）；idle 超时读行。
  • 时间感知：pi 不加载 opencode 插件，改在 prompt 首行拼 <system-context>；opencode 走 hooks/inject-time.js 插件。
  • 技能摘要注入：ClaudeCliClient._build_skill_summary() 扫描技能根目录 SKILL.md 的 frontmatter，注入首轮。

5.4 微信 sidecar（lib/js/wechat-sidecar.mjs）

  • 纯 Node 标准库，零第三方依赖：fetch + node:http + crypto（仅 QR 终端显示尝试 optional import qrcode-terminal）。
  • 双通道：iLink Bot 长轮询收消息（getupdates，带 sync buffer 持久化断点）；本机 HTTP 服务（默认 127.0.0.1:8787）提供 POST /send 供 agent 主动推送微信。
  • 文件归档：CDN 下载 → AES-128-ECB 解密（自动处理 key 格式与无 padding 情形）→ 落盘 FILE_ARCHIVE_DIR → 回执路径。
  • webhook 调用用 node:http 而非 undici fetch：规避 undici 隐含的 5 分钟 headersTimeout，长任务不误报"服务繁忙"（这是有具体线上事故背景的修复）。
  • context_token：持久化在 runtime/wechat/context_tokens.json，用于 iLink 消息上下文续接。

6. 消息处理链路

飞书文本消息（默认 pi 后端 + 流式）

  1. 飞书 SDK 长连接收到事件 → FeishuWsClient 线程回调 → run_coroutine_threadsafe 投递到 asyncio loop
  2. FeishuWebhookHandler.handle_event 生成 trace_id，create_task 后台处理（3 秒内返回满足平台约束）
  3. 去重（message_id）→ 文件消息直接归档返回路径
  4. /stop → 清队列 + 杀任务；/daily /remind → 调度器；/命令 → 直接回复；/skills → 摘要；普通消息 → 进入会话队列
  5. 队列 worker 串行执行 LLM job：task_registry.start 注册 → 拼历史 + 当前消息（图片先下载为本地路径）
  6. 流式：AgentRouter → PiCliClient 每轮 spawn pi --mode json，逐行解析 JSONL，text_delta 每 80 字符切片 yield
  7. 若命中图片请求关键词，watcher 每 1s 扫描生成图片目录，有新图即推送，完成后自动 cancel agent
  8. 完整答案按渠道格式化：markdown 卡片 → 失败降级 chain → 超长分段（块边界优先）→ 图片上传/回复
  9. 写回 SessionManager（pi/opencode 侧会话由后端自管，codeClaw 只补 FIFO 副本），清理下载的临时图片

微信文本消息

流程对称，差异点：sidecar 长轮询收消息 → POST /webhook/wechat → handler 挂起请求等任务完成 → 返回 replies 数组 → sidecar 逐条 sendmessage；不具备图片上传能力；/remind 明确禁用。

  • pi/opencode 原生会话续接，codeClaw 只维护映射；备选后端由 codeClaw 做 FIFO（50 轮）拼接。
