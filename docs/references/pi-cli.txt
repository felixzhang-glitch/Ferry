# pi CLI 参考

pi（Pi Coding Agent，https://pi.dev）是 Ferry 的唯一后端。下文协议行为基于既有 0.84.2 验证记录；2026-09-11 用本机 `pi --version`、`pi --help` 核对版本与参数，未重新请求真实模型或渠道

## 基本用法

```bash
# 交互模式
pi

# 非交互纯文本，处理完即退出
pi -p "列出 src 下的 ts 文件"

# 非交互 JSONL 事件流（Ferry 使用；不需要额外加 -p）
pi --mode json "<prompt>"

# 常驻双向 RPC（Ferry 暂未使用）
pi --mode rpc

# 指定模型（provider/model-id，可带 :thinking 后缀）
pi --model bailian/deepseek-v4-flash-0731 "<prompt>"

# 会话：续接上一个 / 交互式选择 / 指定文件或 UUID 前缀 / 分叉 / 不落盘
pi --continue "<prompt>"
pi --resume
pi --session <path|id> "<prompt>"
pi --fork <path|id> "<prompt>"
pi --no-session "<prompt>"

# 指定精确会话 ID，不存在则以该 ID 新建（Ferry 使用）
pi --session-id <id> "<prompt>"

# 追加系统提示，可多次；值可以是文本，也可以是文件路径（读取文件内容）
pi --append-system-prompt <file-or-text> "<prompt>"

# 完整替换系统提示
pi --system-prompt "<text>" "<prompt>"

# 工具白名单（只读模式）/ 黑名单 / 全关
pi --tools read,grep,find,ls -p "<prompt>"
pi --exclude-tools bash "<prompt>"
pi --no-tools "<prompt>"

# 推理强度
pi --thinking off|minimal|low|medium|high|xhigh|max "<prompt>"

# 信任项目级 .pi/ 资源（非交互模式默认不信任）
pi --approve "<prompt>"

# 模型列表 / 版本 / 扩展管理
pi --list-models [search]
pi --version
pi list / pi install <source> / pi remove <source> / pi update [source|self]
```

## Ferry 集成方式

```bash
pi --mode json --session-id <id> [--model <provider/model>] \
   [--thinking <level>] [--tools <list>] \
   --append-system-prompt <rules/system.md> \
   --append-system-prompt <rules/admin.md> \
   --append-system-prompt <runtime/server/memory-context.md> \
   --append-system-prompt "<当前系统时间: …>" \
   --approve <prompt>
```

| 参数 | Ferry 的用法 |
|------|-----------------|
| `--mode json` | 输出 JSONL 事件流，逐行读 stdout |
| `--session-id` | 会话 ID **由 Ferry 生成**（uuid4 hex），按渠道会话 key 持久化后复用 |
| `--append-system-prompt` | 规则、长期记忆与时钟的每轮注入通道。值可以是文件路径（读内容），也可以是直接给的文本——时间走文本，每轮进程新生成一次 |
| `--approve` | 非交互模式不弹信任提示，默认按 `defaultProjectTrust: ask` **忽略**项目级资源，需显式信任 |
| `--tools` | 留空不传。它是 allowlist，传了会把扩展工具一起排除 |

- 装配：`app.main` 直接实例化 `PiCliClient`；`core.agent.types` 提供 `AgentClient` Protocol 与异常；不再经过路由器
- 工作目录：`PI_WORK_DIR` 是最终 cwd，默认 `./runtime/codex-workdir/pi`；未设新键时兼容旧 `<CODEX_WORK_DIR>/pi`
- 输出读取：逐行 stdout，单行 idle 超时由 `PI_IDLE_TIMEOUT_SECONDS` 控制；每次 CLI 尝试还受总时限约束，见 [可靠性说明](../RELIABILITY.md)
- 会话管理：pi 自行管理历史与压缩，客户端维护 key → pi ID 映射；两个渠道每轮只传当前 user，`SessionManager` 仅存 key 与待处理附件
- 技能：`app.skills` 扫 `SKILL_ROOTS` 生成首轮摘要，模型再用内建 `read` 读 SKILL.md 正文，不依赖其它 CLI
- 时间感知：`app/clock.py` 生成文本，经 `--append-system-prompt` 走 system 通道，不拼 prompt 首行，避免时间戳在 transcript 中逐轮累积或进入压缩摘要

| 变量 | 默认值 | 说明 |
|------|--------|------|

| `PI_TOOLS` | （空） | `--tools` allowlist，留空不传 |

| `PI_SESSION_STORE_PATH` | `./runtime/server/pi-sessions.json` | session ID 映射持久化 |
| `PI_WORK_DIR` | `./runtime/codex-workdir/pi` | 最终 cwd，不再自动追加 `/pi` |
| `PI_STREAM_READ_LIMIT_BYTES` | `262144` | stdout 读取缓冲上限 |
| `PI_MAX_RETRIES` | `2` | 客户端重试上限 |
| `PI_RETRY_BACKOFF_SECONDS` | `1.0` | 重试退避基数 |
| `PI_CIRCUIT_BREAKER_THRESHOLD` | `5` | 熔断失败阈值 |
| `PI_CIRCUIT_BREAKER_COOLDOWN_SECONDS` | `30` | 熔断冷却时间 |
| `GENERATED_IMAGES_DIR` | `~/.codex/generated_images` | 既有生成图片发现目录，保留默认路径不代表依赖 Codex CLI |

### 旧配置迁移

新键优先；仅以下共享旧键保留回退，非其它后端恢复入口：

| 新键 | 旧键回退 |
|------|----------|
| `PI_WORK_DIR` | `CODEX_WORK_DIR` 的值追加 `/pi`，保留旧 cwd 语义 |
| `PI_STREAM_READ_LIMIT_BYTES` | `CODEX_STREAM_READ_LIMIT_BYTES` |
| `PI_MAX_RETRIES` | `CODEX_MAX_RETRIES` |
| `PI_RETRY_BACKOFF_SECONDS` | `CODEX_RETRY_BACKOFF_SECONDS` |
| `PI_CIRCUIT_BREAKER_THRESHOLD` | `CODEX_CIRCUIT_BREAKER_THRESHOLD` |
| `PI_CIRCUIT_BREAKER_COOLDOWN_SECONDS` | `CODEX_CIRCUIT_BREAKER_COOLDOWN_SECONDS` |
| `GENERATED_IMAGES_DIR` | `CODEX_GENERATED_IMAGES_DIR` |

后端选择配置与状态文件不再参与运行；渠道、记忆和 provider 凭证继续保留。不要自动迁移现有 cwd、`PI_SESSION_STORE_PATH` 或 `PI_CODING_AGENT_DIR`，更不能删除旧运行目录或用户数据；pi 会话按 cwd 组织，换目录可能破坏续接。完整边界见 [单 pi 接入](../routing.md)

## 自定义模型注册

注册表是仓内 `conf/pi/models.json`，服务启动时自动同步到 `~/.pi/agent/models.json`。pi 不内置百炼 provider，必须整条注册：

```json
{
  "providers": {
    "bailian": {
      "name": "阿里云百炼",
      "baseUrl": "https://dashscope.aliyuncs.com/compatible-mode/v1",
      "api": "openai-completions",
      "apiKey": "$DASHSCOPE_API_KEY",
      "compat": {
        "supportsDeveloperRole": false,
        "supportsReasoningEffort": true
      },
      "models": [
        {
          "id": "deepseek-v4-flash-0731",
          "name": "DeepSeek V4 Flash 0731 (百炼)",
          "reasoning": true
        }
      ]
    }
  }
}
```

- `apiKey` 支持三种取值：字面量、`"$ENV_VAR"` 环境插值、`"!command"` 执行命令取 stdout。
  这里用环境插值，密钥只落在 gitignored 的 `conf/.env`，不进仓库也不进 `ps`。
- `compat.supportsDeveloperRole: false` 是给 OpenAI 兼容端点的保守设置：不发 `developer` role
  （改发 `system`）。`compat.supportsReasoningEffort: true` 放行 `reasoning_effort` 下发，
  强度由 `--thinking` / `PI_THINKING` 控制（见下文推理强度一节）。
- `contextWindow: 1000000` / `maxTokens: 16384` 已显式声明（`--list-models` 显示 1M / 16.4K）。
  依据：百炼公告 DeepSeek-V4-Flash-0731「原生 1M 超长上下文，最大输出 384K」，官方 API 文档
  则说 `max_tokens` 与 `thinking_budget` 合计上限 393,216。`maxTokens` 取 16384（= pi 旧默认值）
  是为了把隐式默认变显式，IM 回复场景够用，同时钉住压缩摘要的输出预算。
  两个字段未填时用 pi 默认 128000 / 16384，填错会让自动压缩过早或过晚触发。
- 验证注册结果：`PI_OFFLINE=1 pi --list-models bailian`。models.json 在每次打开 `/model` 时重载，
  改完不用重启 pi（但 Ferry 侧改 `.env` 需要重启服务）。

### DeepSeek 官方（provider `deepseek`）

`deepseek` 是 pi 内置 provider（`baseUrl: https://api.deepseek.com`、`openai-completions`、
`DEEPSEEK_API_KEY` 环境鉴权），但内置目录只有 `deepseek-v4-flash` / `deepseek-v4-pro`，
没有 `deepseek-flash`，所以在注册表里补一条：

```json
{
  "providers": {
    "deepseek": {
      "name": "DeepSeek 官方",
      "baseUrl": "https://api.deepseek.com",
      "api": "openai-completions",
      "apiKey": "$DEEPSEEK_API_KEY",
      "models": [
        {
          "id": "deepseek-flash",
          "name": "DeepSeek V4.1 Flash",
          "reasoning": true,
          "input": ["text", "image"],
          "contextWindow": 1000000,
          "maxTokens": 16384
        }
      ]
    }
  }
}
```

- 合并语义：内置模型保留，自定义按 `id` upsert。`PI_OFFLINE=1 pi --list-models deepseek` 实测三条并列，
  `deepseek-flash` 显示 1M / 16.4K / thinking yes / images yes。
- **不写 `compat`**：pi 按 provider id（或 baseUrl 含 `deepseek.com`）自动判定 `thinkingFormat: "deepseek"`、
  `maxTokensField: "max_tokens"`、`supportsDeveloperRole: false`、`supportsStore: false`、
  `requiresReasoningContentOnAssistantMessages: true`，且 `supportsReasoningEffort: true`。本地 mock 抓到的
  真实请求体印证：只有 `max_tokens: 16384`（无 `max_completion_tokens`）、消息角色只有 `system`/`user`。
- 请求路径是 `<baseUrl>/chat/completions`（**不带 `/v1`**）；实测 `https://api.deepseek.com/chat/completions`
  与 `/v1/chat/completions` 都返回 200，所以 baseUrl 照 pi 内置值原样写即可。
- `maxTokens: 16384` 沿用百炼条目的取舍（IM 回复够用 + 钉住压缩摘要输出预算），不是端点上限。
- 图文：`input: ["text","image"]` 让 pi 接受 `@file` 图片，请求体里是
  `{"type":"image_url","image_url":{"url":"data:image/png;base64,…"}}`；真实调用能正确回答图片颜色。
- 密钥只落 gitignored 的 `conf/.env`（`DEEPSEEK_API_KEY`），由 `app/config.py` 读入、
  `PiCliClient._process_env` 注入 pi 子进程与常驻 worker，不走 `--api-key`、不进 `ps`。
- 验证记录：`runtime/deepseek-switch-verification.json`（mock 抓包 + 真实文本/图片/会话续接三轮）。

## 推理强度 reasoning_effort

pi 的 `--thinking <level>` 对 openai-completions provider 会转成请求体的 `reasoning_effort`，
前提是 models.json 里 `compat.supportsReasoningEffort: true`（为 `false` 时 pi 会把该参数剥掉）。
Ferry 侧由 `PI_THINKING` 控制，默认 `high`，经 [pi_cli.py](../../lib/python/core/agent/pi_cli.py) 的 `--thinking` 下发。

百炼文档原文：

> deepseek-v4-pro、deepseek-v4-flash 和 deepseek-v4-flash-0731 默认开启思考模式。
> 通过 `reasoning_effort` 可调推理强度，可选值 `low`、`medium`、`high`、`xhigh`、`max`，默认 `high`。
> 其中 `low`、`medium` 等同 `high`；`xhigh` 等同 `max`。

即实际只有两档：`{low, medium, high}` → high，`{xhigh, max}` → max。写 `low` 等于不写，
想加深推理只有 `xhigh`/`max` 有效，代价是延迟和 token 上升。因为该模型默认就开思考，
`PI_THINKING=high` 与服务端默认等效，只是把档位变得显式且可调；`PI_THINKING=off` 则关思考。

**「只有两档」仅限百炼 provider。** DeepSeek 官方端点（`deepseek/deepseek-flash`）走 pi 的
`thinkingFormat: "deepseek"`：`PI_THINKING=low` 会原样下发 `reasoning_effort: "low"` 并附
`thinking: {"type":"enabled"}`（本地 mock 抓到的真实请求体确认）；按 pi 源码，`off` 改发
`thinking: {"type":"disabled"}`（未实测）。当前生产取值 `low`。

## 上下文自动压缩

压缩由 pi 自己承担（`core/compaction`），Ferry 零参与。参数写在 `~/.pi/agent/settings.json`，
仓内模板 `conf/pi/settings.json.example`：

```json
{
  "compaction": {
    "enabled": true,
    "reserveTokens": 200000,
    "keepRecentTokens": 150000
  }
}
```

- 触发条件：`contextTokens > contextWindow - reserveTokens`，即 `1000000 - 200000 = 800000`
  （窗口的 80%）。字段缺失时默认 `reserveTokens: 16384` / `keepRecentTokens: 20000`，
  那套默认是按 128K 窗口调的，搭 1M 窗口会变成“几乎不压缩，压一次又只留 20k”。
- 保留策略：从最新往回累计到 `keepRecentTokens`（150k）为止的消息原文保留，更早的交给 LLM
  生成摘要（能与上一次摘要迭代合并）；切点只落在 user/assistant 消息，不切断 tool result。
- 摘要调用的输出上限是 `min(0.8 × reserveTokens, maxTokens)`，即 `min(160000, 16384) = 16384`。
- 两个触发点都在 `AgentSession` 核心里，与运行模式无关，`--mode json` 同样生效：
  `agent_end` 之后；以及发新 prompt 之前（pre-prompt check，对 Ferry 每轮新进程恢复会话的
  模式尤其重要）。另有 overflow 分支：LLM 报上下文溢出时先压缩再自动重试。
- 历史实测：微信主会话在 128K 窗口时以 111,616 为阈值，2026-08-07（tokensBefore=112641）与
  2026-08-14（111738）各触发一次，阈值公式已被真实数据验证。
- Ferry 的 `/compact`、`/compress` 仅提示上下文由 pi 原生管理，不执行压缩，也不伪报成功。
  `SessionManager` 已无 rounds 或手工摘要；需要新上下文时用 `/new`、`/reset`，清附件通知与
  session_key → pi ID 映射，下轮创建新会话，pi 侧旧 transcript 保留。`/backend`、`/pi` 只读状态。
- 注入的 system prompt（`--append-system-prompt` 的 rules + memory + 时钟，约 5.5KB）**不参与压缩**，
  压缩只处理会话消息，它每轮都在场。时钟走这条通道正是看中这点：压缩不会把它折进摘要，
  也不会像 prompt 内联那样在 transcript 里留下几百个互相矛盾的旧时间戳。

## 事件流 schema

`--mode json` 的实测事件序列（0.84.2，bailian provider）：

```
session          首行，含 id / version / cwd；id 即 --session-id 传入的值
agent_start
turn_start
message_start    role=user
message_end      role=user        ← 注意：user 轮也有 message_end
message_start    role=assistant，stopReason=pending
message_update   assistantMessageEvent.type = text_start
message_update   assistantMessageEvent.type = text_delta，delta 只含新增后缀
message_update   assistantMessageEvent.type = text_end
message_end      role=assistant，stopReason=stop，content[].text 为权威终态
turn_end
agent_end        willRetry=false（为 true 时不是真结束）
agent_settled    真正结束标志
```

带工具调用的轮次在 assistant 段额外插入（实测 0.84.2 + deepseek provider，2026-09-22）：

```
message_update   assistantMessageEvent.type = thinking_start / thinking_delta / thinking_end
message_update   assistantMessageEvent.type = toolcall_start / toolcall_delta / toolcall_end
message_end      role=assistant，stopReason=toolUse，content[] 含 thinking + toolCall{id,name,arguments}
tool_execution_start   {toolCallId, toolName, args}            ← 进度提示与计时起点
tool_execution_update  {…, partialResult}                      ← 工具分片输出，Ferry 忽略
tool_execution_end     {toolCallId, toolName, result, isError} ← 进度清除与工具耗时
message_start    role=toolResult，含 toolCallId / toolName / isError
message_end      role=toolResult
turn_end → turn_start（进入下一个模型往返）
```

`stopReason=toolUse` 是中间态，不参与成败判定；判定仍只看最后一条 assistant `message_end`。

Ferry 侧的四条解析规则：

1. 只取 `message_update.assistantMessageEvent.text_delta` 的 `delta` 直接输出，
   `thinking_delta` / `toolcall_delta` 一律丢弃，思考不进回复。
2. `message_end` 必须判 `message.role == "assistant"`，否则会把用户的提问当回复回显。
3. **`--mode json` 的 provider 失败也可能退出 0**，不能只靠退出码判断成功；还要检查
   `message_end.message.stopReason`（`error` / `aborted`）与 `errorMessage`，非零退出同样报错。既有验证示例：

```json
{"type":"message_end","message":{"role":"assistant","content":[],"stopReason":"error",
 "errorMessage":"401: {\"message\":\"Incorrect API key provided...\",\"code\":\"invalid_api_key\"}"}}
```

4. `tool_execution_start` / `tool_execution_end` 用于进度与工具耗时：打 `pi.tool_call`（`tool` / `tool_detail` / `elapsed_ms`）与 `pi.tool_result`（`tool` / `duration_ms` / `is_error`），并经 `chat_stream(on_progress=...)` 把标签推给渠道渲染。`tool_execution_update` 的分片输出一律忽略——每个 chunk 都刷一次卡片会打爆飞书接口

分帧按 `\n` 切即可（Python 的 `readline()` 合规）。不要对整段 stdout 做 `splitlines()`，
它会在 `U+2028`/`U+2029` 上误切。

### 成败判定：以最后一条 assistant message_end 为准（last-wins）

pi 在**同一个进程内**会 auto-retry：第一次尝试可能 `stopReason=error` +
`agent_end.willRetry=true`，重试后再给一条 `stopReason=stop`。所以判定规则是：

- 只看**最后一条** assistant `message_end` 的 `stopReason`。是 `error` / `aborted` 就报错，
  **即使前面已经流出了部分文本**——否则被截断的半截回答会当完整回答发给用户。
- 中间尝试的失败不算失败。不能写成“出现任何错误事件就报错”，那会把重试成功的轮次误判为失败。
- 一条 text_delta 都没有时，用 `message_end.message.content[].text` 兜底输出。
- 流结束后没有任何可用输出即按失败处理，即使出现了 `agent_settled` 也不能静默回空。

## supervisor 下的注意事项

1. 为 `PI_CLI_BIN` 配置服务账号可执行的 pi 路径，生产优先用绝对路径；不要依赖交互 shell 的 PATH。启动只需 pi，不检查其它 agent CLI
2. 确认服务环境的 Node 满足已安装 pi 版本要求（0.84.2 要求 Node ≥ 22.19.0）。若现有 pi 使用固定 Node 版本的 wrapper，不要在此次收敛中覆盖或迁移它
3. spawn 使用 `stdin=DEVNULL`，避免继承 supervisor 未关闭的 stdin pipe 导致 pi 等待 EOF；使用独立进程组并按 trace_id 取消，以回收 pi 启动的子进程。回收与超时行为需要隔离测试
4. 保持服务 HOME、现有 cwd、`PI_CODING_AGENT_DIR` 与 session store 路径不变；留空 agent dir 时 pi 使用服务账号的 `~/.pi/agent`。本次不修改真实配置、用户数据或重启服务
